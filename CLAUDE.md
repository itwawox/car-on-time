# CLAUDE.md — правила разработки Car on Time

Цель этих правил — стабильный, поддерживаемый код, а не красивая первая версия. Каждое изменение проходит один и тот же путь: код → тесты → форматирование → статанализ → документация → Pull Request с зелёными проверками.

## Стек (менять только по согласованию)

| Слой | Что используем |
|---|---|
| Язык и фреймворк | PHP 8.4, Laravel 13 |
| База | MySQL (в тестах — SQLite в памяти) |
| Админка | Filament 4 (внутри — Livewire 3) |
| Публичный сайт | Blade-шаблоны + Tailwind CSS v4 + ванильные ES-модули (`resources/js`), сборка Vite 8 |
| Фон | очередь `database` + планировщик (`routes/console.php`), на хостинге — CRON раз в минуту |
| Пакеты | Spatie Media Library (файлы), Spatie Honeypot (антиспам), Laravel Scout со своим движком `smart` (поиск) |
| Качество | Pest 4 (тесты), Pint (форматирование), Larastan 3 (статанализ, уровень 5) |
| Помощник для AI | Laravel Boost (`AGENTS.md`, `.mcp.json`, `boost.json`) |
| Хостинг | обычный хостинг reg.ru, не VPS: нет root, Node.js и supervisor; выкладка — GitHub Actions + `deploy/release.sh` |

Не добавлять на публичный сайт Inertia, Vue, React или Livewire и не менять зависимости без согласования.

## Архитектура: куда класть новый код

- **Controller** (`app/Http/Controllers`) — тонкий: принять запрос, вызвать Action или Service, вернуть ответ. Бизнес-логики в контроллере нет.
- **Form Request** (`app/Http/Requests`) — вся валидация входящих данных и сообщения об ошибках. В новом коде валидация в контроллере запрещена. Старые контроллеры с `$request->validate()` переводим на Form Request, когда их трогаем.
- **Action** (`app/Actions`) — одна бизнес-операция: один класс, один публичный метод `handle()`. Пример: `CreateBooking`, `ExtendBooking`. Action можно вызвать из контроллера, команды, Job или теста.
- **Service** (`app/Services`) — расчёты и интеграции, которыми пользуются многие: `QuoteCalculator` — единственное место расчёта цены; `Bitrix24Sync`, `SmsSender`, `PrepaymentService`.
- **Support** (`app/Support`) — небольшие помощники без состояния: `Availability`, `Phone`, `Attribution`.
- **Job** (`app/Jobs`) — любой вызов внешнего сервиса (CRM, SMS): только через очередь, с записью в `IntegrationLog` и с `rescue()`, чтобы сбой сервиса не ломал заявку клиента.
- **Policy** (`app/Policies`) — права на модели в новом коде. Уже работают: роли админки — `User::AREAS` и трейт `App\Filament\Concerns\RestrictedToArea`; клиент в кабинете — `CustomerSession::owns()`.
- **Model** — связи с типами (`@return BelongsTo<Car, $this>`), `casts()`, области видимости (`scopeActive`). Тяжёлой логики в модели нет.
- **Filament Resource / Page** — админка; доступ через `RestrictedToArea`.
- Секреты интеграций — только `Setting::putSecret()` / `Setting::secret()` (зашифрованы). Никогда не в коде и не в git.
- Все тексты и цифры, которые видит посетитель, — из `Setting::get()` с текстом по умолчанию, чтобы их можно было менять в админке.

## Тесты — обязательны

- Любое изменение поведения сопровождается тестом на **Pest** (`tests/Feature` — почти всё, `tests/Unit` — чистые функции без базы). Старые тесты — классы PHPUnit — не переписываем, Pest запускает их как есть.
- Нашли баг — сначала пишем тест, который его воспроизводит (красный), потом исправляем (зелёный).
- Внешние сервисы — только `Http::fake()`, файлы — `Storage::fake()`, время — `$this->travel()`. Тест никогда не ходит в настоящий Битрикс24, SMS или ЮKassa.
- Проверяем поведение (что видит пользователь, что сохранилось, что ушло во внешний сервис), а не внутреннее устройство.

## Обязательные команды после каждого изменения

```bash
./vendor/bin/pint        # 1. форматирование — исправляет стиль кода сам
./vendor/bin/phpstan     # 2. статанализ Larastan — ошибок быть не должно
./vendor/bin/pest        # 3. все тесты — должны быть зелёными
```

Или одной командой, в режиме проверки, как в GitHub: `composer check`.
Если менялись CSS или JS — ещё `npm run build`.

**Larastan:** новые ошибки **не добавляем** в `phpstan-baseline.neon` и не глушим `@phpstan-ignore` — исправляем причину. Baseline хранит только замечания к коду, написанному до подключения Larastan, и должен со временем уменьшаться.

## Процесс

- Работа — в отдельной ветке → коммит → Pull Request. Вливаем только при зелёных проверках GitHub Actions (Pint, Larastan, Pest, `composer audit`, `npm audit`).
- Любое изменение, которое влияет на выкладку, настройку или работу сайта, — с правкой документации (`resources/docs/developers/*.md`, в админке «Документация») в том же коммите.
- Миграции только добавляют и меняют структуру. На хостинге никогда не запускать `migrate:fresh`, `migrate:refresh`, `db:wipe`, `db:seed`.
- Не коммитить `.env`, копии базы (`storage/backups`), ключи и пароли — репозиторий публичный.
