# Автотесты: что это и как с ними работать

> Подробно, с разбором каждого теста и практикой, — в **Документация → Курс**, уроки 4–6. Там же поиск сразу по курсу и этой документации.

## Что такое автотест

Автотест — маленькая программа, которая проверяет сайт **вместо человека**. Например:

- «открой страницу машины — на ней должна быть кнопка „Оставить заявку“»;
- «отправь заявку без телефона — сайт должен показать ошибку и не сохранить её»;
- «промокод на 10% — сумма должна уменьшиться ровно на 10% от аренды»;
- «менеджер не может подтвердить бронь на машину, которая уже занята».

Сейчас у сайта **больше 190 таких проверок**. Все вместе они проходят примерно за 10 секунд. Руками на то же самое ушло бы несколько часов, и что-нибудь обязательно забылось бы.

Главная польза: вы меняете что-то в одном месте, а тесты сразу скажут, если это сломало что-то в другом.

## Где они лежат

Папка `tests/Feature`, по файлу на тему:

| Файл | Что проверяет |
|---|---|
| `BookingUxTest.php` | заявка на бронь, страница «Спасибо», второй шаг |
| `QuoteCalculatorTest.php` | расчёт цены: сезоны, доставка, ночной тариф |
| `PromoCodeTest.php` | промокоды |
| `BookingWorkflowTest.php` | занятость машин, статусы, напоминания менеджерам |
| `Bitrix24IntegrationTest.php`, `CustomerNotificationsTest.php`, `PrepaymentTest.php` | Битрикс24, SMS, ЮKassa |
| `AdminRolesTest.php` | кто что видит в админке |

## Как запустить тесты у себя

В Терминале, в папке проекта:

```bash
cd ~/Herd/rentacar
./vendor/bin/pest
```

(`php artisan test` делает то же самое.) А перед пушем — все проверки сразу, как их запускает GitHub:

```bash
composer check      # форматирование (Pint) + статанализ (Larastan) + тесты (Pest)
```

Что вы увидите:

- строки с зелёным **✓ PASS** — проверка прошла;
- красный **⨯ FAIL** — проверка не прошла. Ниже будет написано, **какой тест**, **что ожидалось** и **что получилось на самом деле**, например: `Expected response status code [200] but received 500` — «ждали, что страница откроется, а она выдала ошибку»;
- в конце итог: `Tests: 162 passed` — всё хорошо.

Запустить только один файл или один тест (быстрее, когда работаете над конкретной частью):

```bash
./vendor/bin/pest tests/Feature/PromoCodeTest.php
./vendor/bin/pest --filter=test_fixed_discount_never_exceeds_rent
```

**Тесты не трогают ваши данные.** Для каждого запуска создаётся временная пустая база в памяти (настройка в `phpunit.xml`), после запуска она исчезает. Внешние сервисы (Битрикс24, SMS, ЮKassa, Telegram) в тестах **подменяются заглушками**. Настоящие SMS не уходят, настоящие сделки не создаются.

Если тесты падают с ошибкой `Vite manifest not found` — не собраны стили: выполните `npm run build`.

## Что делать, если тест красный

Прочитайте сообщение под FAIL. Возможны два случая:

1. **Вы случайно сломали то, что работало.** Исправьте код, запустите тесты снова.
2. **Вы специально изменили поведение сайта** (например, убрали поле из формы), а тест проверяет старое поведение. Тогда поправьте тест под новое поведение. Это нормально: тест — описание того, как сайт **должен** работать.

Не удаляйте тест только ради того, чтобы он «стал зелёным», если не понимаете, что он проверяет.

## Автотесты на GitHub («галочки зелёные»)

Те же проверки GitHub запускает **сам**, на своём компьютере, при каждом пуше и каждом Pull Request: форматирование (Pint), статанализ (Larastan), тесты (Pest) и проверку библиотек на известные уязвимости (`composer audit`, `npm audit`). Это описано в файле `.github/workflows/tests.yml`.

Где смотреть результат:

- **На странице Pull Request**, внизу, над кнопкой Merge:
  - зелёная галочка и «All checks have passed» — тесты прошли, можно вливать;
  - красный крестик и «Some checks were not successful» — что-то сломано, **вливать нельзя**;
  - жёлтый кружок — тесты ещё идут (около минуты).
- **В списке коммитов** (вкладка Commits) рядом с каждым коммитом та же иконка: ✓, ✗ или ●.
- **Вкладка Actions** — история всех запусков.

Как понять, что сломалось: нажмите на красный крестик → **Details** → откроется журнал. Прокрутите до красных строк FAIL — там то же сообщение, что вы увидели бы у себя в Терминале.

Страховка: выкладка на хостинг (`deploy.yml`) сама запускает тесты и **не начнётся**, если они красные. Сломанный код на боевой сайт не попадёт, даже если его случайно влили.

## Как тестировать при разработке — порядок работы

1. Перед началом: `./vendor/bin/pest` — убедиться, что всё зелёное (если нет — сначала разобраться).
2. Делаете изменение и **сразу** пишете или правите тест, который его проверяет.
3. Запускаете тесты своей темы (`--filter` или один файл), пока не станут зелёными.
4. Перед коммитом — все проверки: `composer check`.
5. Пушите → на Pull Request ждёте зелёную галочку → Merge.

Правило для багов: **нашли ошибку — сначала напишите тест, который её воспроизводит** (он будет красным), потом исправьте код (тест станет зелёным). Эта ошибка больше не вернётся незамеченной.

## Как написать свой тест

Тесты пишем на **Pest** — это короткая запись тех же проверок. Старые тесты в проекте написаны классами PHPUnit (их видно по `class …Test extends TestCase`). Pest запускает и их, переписывать не нужно, но **новые пишем на Pest**.

Создать файл:

```bash
php artisan make:test CarColorTest --pest
```

Пример: проверяем, что цвет машины виден в карточке. Это учебный пример к полю «Цвет» из раздела «Изменения базы данных»: пока такого поля нет, тест будет красным — ровно так и выглядит «сначала тест, потом код».

```php
<?php

use App\Models\Brand;
use App\Models\Car;

it('shows car color on the car page', function () {
    // 1. Подготовка: создаём машину с цветом (база в каждом тесте чистая — это настроено в tests/Pest.php)
    $brand = Brand::query()->create(['slug' => 'kia', 'name' => 'Kia']);
    Car::query()->create([
        'brand_id' => $brand->id, 'name' => 'Kia Rio', 'slug' => 'kia-rio',
        'gearbox' => 'at', 'seats' => 5, 'status' => 'published', 'min_days' => 1,
        'color' => 'Белый',
    ]);

    // 2. Действие: открываем страницу машины
    $response = $this->get('/avto/kia-rio');

    // 3. Проверка: страница открылась, и на ней есть цвет
    $response->assertOk()->assertSee('Белый');
});
```

Живые примеры Pest-тестов в проекте: `tests/Feature/SearchWeightsTest.php`, `tests/Unit/PhoneAndAttributionTest.php` (там же «датасеты» — одна проверка на много входных значений).

Три шага любого теста: **подготовка** (создать данные), **действие** (открыть страницу, отправить форму), **проверка** (что получилось). Текст в `it('…')` описывает, что должно быть.

Самые полезные проверки:

| Проверка | Что значит |
|---|---|
| `assertOk()` | страница открылась без ошибки |
| `assertSee('текст')` / `assertDontSee('текст')` | текст есть / нет на странице |
| `assertRedirect()` | после формы — переход на другую страницу |
| `assertForbidden()` | доступ запрещён (например, без входа в админку) |
| `expect($значение)->toBe(ожидали)` | значение совпадает (Pest) |
| `$this->assertSame(ожидали, получили)` | то же в старых тестах (PHPUnit) |
| `$this->assertDatabaseHas('bookings', ['phone' => '…'])` | запись появилась в базе |

Можно попросить Claude: «добавь тест на …» — он напишет его по этому же образцу.
