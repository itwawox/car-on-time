# Переезд на car-on-time.ru

Клиент утвердил тестовый сайт. Теперь переносим **код, базу и картинки** на боевой домен. Старый сайт на `car-on-time.ru` данных, которые нужно сохранить, не содержит, но **до последней минуты продолжает работать**: новый сайт готовим рядом, в отдельной папке, а в конце переключаем домен.

В примерах:

- `u1111111` и `server111.hosting.reg.ru` — аккаунт reg.ru боевого сайта;
- `u2222222` и `server222.hosting.reg.ru` — аккаунт тестового сайта;
- новая папка боевого сайта — `car-on-time`.

Весь переезд — около 2 часов. Клиенты заметят только минуту переключения домена (этап 6).

## Этап 0. Страховка: копия старого сайта

Данные старого сайта не нужны, но архив на месяц не помешает. Панель reg.ru аккаунта `u1111111` → **«Резервные копии»** → скачать сайт и базу. Либо:

```bash
ssh u1111111@server111.hosting.reg.ru "tar czf ~/old-site-backup.tar.gz www/car-on-time.ru"
scp u1111111@server111.hosting.reg.ru:old-site-backup.tar.gz ~/Backups/
```

Старую папку сайта и старую базу **не удаляем** до конца месяца: если что-то пойдёт не так, вернём домен на них (этап 6).

## Этап 1. Подготовить хостинг боевого сайта

Всё как в уроке «Первый запуск тестового сайта», шаги 2–5 и 11, но для аккаунта `u1111111`:

1. **PHP 8.4** для `car-on-time.ru` и лимиты загрузки (`upload_max_filesize = 10M`, `post_max_size = 48M`).

> Внимание: переключение PHP может сломать **старый** сайт, если он написан под старую версию. Тогда переключайте PHP в этапе 6, вместе с доменом.

2. **Новая база**, например `u1111111_car`. Старую базу не трогаем.
3. **SSH** и **свой ключ** для выкладки:

```bash
ssh-keygen -t ed25519 -f ~/.ssh/car-on-time-deploy -C "github-deploy-prod"
ssh-copy-id -i ~/.ssh/car-on-time-deploy.pub u1111111@server111.hosting.reg.ru
```

4. GitHub → **Settings → Environments → New environment** → `production`. Секреты — как для staging, но с данными `u1111111`:

| Имя | Значение |
|---|---|
| `DEPLOY_HOST` | `server111.hosting.reg.ru` |
| `DEPLOY_USER` | `u1111111` |
| `DEPLOY_PATH` | `/var/www/u1111111/data/car-on-time` — **новая** папка, не папка старого сайта |
| `DEPLOY_PHP` | `/opt/php/8.4/bin/php` |
| `DEPLOY_SSH_KEY` | `cat ~/.ssh/car-on-time-deploy` |

Переменная среды `DEPLOY_URL` = `https://car-on-time.ru`.

> Совет: в настройках среды `production` включите **Required reviewers** и укажите себя. Тогда GitHub перед каждой выкладкой на боевой сайт будет ждать вашего нажатия «Approve».

## Этап 2. Код в ветку main

Ветка `main` — то, что работает на боевом сайте. Сейчас в ней старая версия; вливаем утверждённую `dev`:

1. GitHub → **Pull requests → New pull request** → `base: main` ← `compare: dev`.
2. Дождитесь зелёной галочки проверок → **Merge pull request**.
3. GitHub начнёт выкладку в `production` и **остановится** на «На хостинге нет файла .env». Так и должно быть: файлы залиты в новую папку, старый сайт по-прежнему работает.

## Этап 3. .env боевого сайта

```bash
ssh u1111111@server111.hosting.reg.ru
cd car-on-time
cp .env.example .env
nano .env
```

```dotenv
APP_ENV=production
APP_DEBUG=false
APP_URL=https://car-on-time.ru

DB_HOST=localhost
DB_DATABASE=u1111111_car
DB_USERNAME=u1111111_car
DB_PASSWORD=пароль-новой-базы
```

```bash
/opt/php/8.4/bin/php artisan key:generate
exit
```

**Новый** `APP_KEY`: не копируйте ключ тестового сайта. Боевые ключи CRM, SMS и оплаты будут зашифрованы своим ключом, и утечка с тестового сайта их не раскроет. Сохраните `.env` в менеджер паролей.

Запустите выкладку снова: **Actions → Run workflow** → среда `production`, что выложить — `main`. Она создаст таблицы в новой базе.

## Этап 4. База: с тестового сайта на боевой

Клиент утвердил — данные на тестовом сайте **заморожены** (прошлый урок).

**На тестовом сайте — копия:**

```bash
ssh u2222222@server222.hosting.reg.ru "cd car-on-time-dev && /opt/php/8.4/bin/php artisan backup:database"
```

**Скачать к себе** (аккаунты разные, поэтому через ваш компьютер):

```bash
mkdir -p ~/Perenos
scp "u2222222@server222.hosting.reg.ru:car-on-time-dev/storage/backups/db-*.sql.gz" ~/Perenos/
ls ~/Perenos                    # нужна самая свежая копия
```

**Отправить на боевой и загрузить:**

```bash
scp ~/Perenos/db-2026-10-15_18-00-00.sql.gz u1111111@server111.hosting.reg.ru:car-on-time/storage/backups/
ssh u1111111@server111.hosting.reg.ru
cd car-on-time
/opt/php/8.4/bin/php artisan down
gunzip -c storage/backups/db-2026-10-15_18-00-00.sql.gz | mysql -u u1111111_car -p u1111111_car
/opt/php/8.4/bin/php artisan migrate --force
/opt/php/8.4/bin/php artisan queue:clear
/opt/php/8.4/bin/php artisan integrations:disable --force
/opt/php/8.4/bin/php artisan optimize:clear
/opt/php/8.4/bin/php artisan optimize
/opt/php/8.4/bin/php artisan up
exit
```

Зачем каждая команда:

- `mysql … -p` спросит пароль **боевой** базы (из `.env` боевого сайта). Имя базы другое, чем на тестовом, и это нормально;
- `migrate --force` — если в `main` есть миграции новее копии;
- `queue:clear` — выбросить задания, которые могли приехать из очереди тестового сайта;
- `integrations:disable --force` — пока всё выключено, включим по одной на этапе 6;
- `optimize:clear` — сбросить кэш, приехавший с тестового сайта.

## Этап 5. Картинки: с тестового сайта на боевой

Тоже через компьютер:

```bash
rsync -avz u2222222@server222.hosting.reg.ru:car-on-time-dev/storage/app/public/ ~/Perenos/public/
rsync -avz ~/Perenos/public/ u1111111@server111.hosting.reg.ru:car-on-time/storage/app/public/
```

Документы клиентов (`storage/app/private`) с тестового сайта **не переносим**: там только тестовые загрузки.

Адреса картинок в базе хранятся без домена (`/storage/…`), поэтому после смены домена ничего переписывать не нужно.

## Этап 6. Переключить домен (минута простоя)

1. Панель reg.ru `u1111111` → «Сайты» → `car-on-time.ru` → **Корневая директория** → `/var/www/u1111111/data/car-on-time/public`.
2. Если PHP ещё не 8.4 — переключите сейчас.
3. SSL уже был у старого сайта — проверьте, что замочек на месте.
4. **CRON:** удалите задания старого сайта и добавьте новое:
   `/opt/php/8.4/bin/php /var/www/u1111111/data/car-on-time/artisan schedule:run` — каждую минуту.

Сразу после переключения сайт уже принимает заявки: они сохраняются в админке (**Заявки → Бронирования**), даже пока интеграции выключены. Поэтому следующий этап делайте сразу.

**Откат**, если что-то пошло совсем не так: верните корневую директорию на папку старого сайта и прежнюю версию PHP. Старый сайт снова в эфире, спокойно разбираемся.

## Этап 7. Навести порядок и включить интеграции

Админка — https://car-on-time.ru/admin. Логины и пароли — те же, что на тестовом сайте (сотрудники переехали вместе с базой).

1. **Тестовые заявки и обращения** — удалить: **Заявки → Бронирования** и **Заявки → Обращения** → отметить → «Удалить». Если за эти минуты пришла настоящая заявка — не удалите её случайно, смотрите на дату.
2. **Сотрудники** (Интеграции → Сотрудники) — выключить лишних, сменить простые пароли.
3. **Интеграции → Интеграции** — ключи тестового сайта здесь **не расшифруются** (другой `APP_KEY`), поэтому введите боевые заново:
   - Telegram-бот и чат;
   - Битрикс24;
   - SMS;
   - ЮKassa.

   Включайте **по одной** и проверяйте тестовой заявкой: пришло в Telegram? Появилась сделка в Битрикс24? Пришла SMS?
4. **Яндекс Метрика** — номер счётчика в настройках (на боевом сайте она подключается сама).
5. Удалите тестовые заявки, созданные при проверке.

## Этап 8. Проверка после запуска

- [ ] https://car-on-time.ru открывается, замочек HTTPS.
- [ ] Каталог, карточка машины, фото на месте.
- [ ] Заявка отправляется, приходит в Telegram, CRM и SMS. Проверочную заявку потом удалить.
- [ ] https://car-on-time.ru/admin — вход работает.
- [ ] https://car-on-time.ru/robots.txt **не** содержит `Disallow: /` и указывает карту сайта.
- [ ] https://car-on-time.ru/sitemap.xml — адреса с `car-on-time.ru`, а не `dev.void-web.ru`.
- [ ] Старые адреса ведут на новые (правила — **SEO → Редиректы**).
- [ ] В Метрике через 5–10 минут видны визиты.
- [ ] Яндекс Вебмастер → «Файлы Sitemap» → отправить на переобход.
- [ ] Через час в админке **Интеграции → Журнал обмена** нет ошибок.
- [ ] Через сутки в `storage/backups` появилась ночная копия (CRON работает).

## После переезда

- Ветка `main` = боевой сайт, ветка `dev` = тестовый. Дальше всё по уроку «Жизнь после запуска».
- Удалите `~/Perenos` у себя: там копия базы с данными.
- Старый сайт и его базу удалите через месяц, когда будет ясно, что откат не нужен.
